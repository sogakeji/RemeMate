## 1. 项目定位

RemeMate 是**多用户多语言生词学习平台**。每个用户构建自己的词库，通过被动曝光（Bark 推送 / 私人播客）+ 主动复习（SRS 三按钮 + AI 助教 + 造句练习）形成闭环。后期加入社交属性（关注、打卡、排行榜）提升粘性。

**与 MemoBuddy 的关系**：MemoBuddy（`memo.8853588.xyz`，`memobuddy` 分支）是作者个人单用户私站，与 RemeMate 代码库**完全独立**，继续维护，作为"作者自用测试田"。RemeMate 可从 MemoBuddy 搬已验证模块（SRS scheduler、DeepSeek cleaning、bark 推送等），搬来即是 RemeMate 的代码，不保留上游标识。

## 2. 硬约束（不讨论，直接写进架构）

### 2.1 独立代码库

- 全新 Git 仓库，不 fork WordNest，不是 MemoBuddy 的 branch
- 代码内不出现 `memobuddy` / `wordnest` 标识；服务名、路径、env 变量全用 `rememate`
- 仓库名：`rememate`（私有 GitHub）

### 2.2 数据库：PostgreSQL

- 所有用户数据共享**一个 Postgres 实例**，用 `user_id` FK 隔离
- **不再用 per-user SQLite 文件**——告别 `db.engines[None]` 全局 mutate 和单 worker 约束
- Schema 迁移用 **Flask-Migrate（Alembic）**，不手写 ALTER TABLE
- Gunicorn 多 worker 从一开始就合法（Postgres 处理并发锁）

### 2.3 部署：与 MemoBuddy 同机，逻辑强隔离

- **开发阶段**：纯本地开发，Postgres 装本地，不依赖任何云机
- **早期上线**：部署到现有 MemoBuddy 云机（43.156.210.229），不新开 VPS——P1 用户少，资源足够，新开机器只增加运维负担
- **朋友测试**：在 MemoBuddy 私站（`memo.8853588.xyz`）加 Basic Auth 账号即可过渡，无需提前部署 RemeMate
- **隔离方式**：Linux 用户级 + 独立 Postgres DB + 独立 systemd + 独立 nginx server block（详见 §6）
- **不共用**：SECRET_KEY、DATA_ENCRYPTION_KEY、数据库用户、端口、日志目录、备份目录均独立
- **MemoBuddy 继续独立运行**：不合并代码，不合并数据；RemeMate 只复用 MemoBuddy 验证过的模块代码

**迁出触发条件**（满足任一条再考虑独立 VPS）：
- RemeMate 开放公开注册
- 活跃用户 50–100+，dispatch 开始影响主机负载
- Session Pad / WebSocket 上线（P2）
- AI / 音频生成影响 MemoBuddy 响应
- 出现安全顾虑：RemeMate 漏洞可能影响同机的 Bitwarden 数据

> **注**：Bitwarden 与 RemeMate 同机的潜在风险——RemeMate 是对外服务，一旦有漏洞可能波及 Bitwarden 数据库。开放注册前应优先将 Bitwarden 迁到独立机器（Bitwarden 是静态服务，迁移成本低），而非将 RemeMate 迁走。

### 2.4 Python + Flask（沿用已验证技术栈）

- Flask + SQLAlchemy + Gunicorn
- 鉴权：**Flask-Login**（session-based，不上 JWT，无移动端 app 需求）
- 流式 AI 响应继续用 Flask SSE（已在 MemoBuddy 验证可行）
- **CSRF**：所有 `hx-post` / 表单 POST 必须带 CSRF token，使用 Flask-WTF 或自定义 `X-CSRFToken` header；HTMX 站点不加 CSRF 是高危漏洞
- 测试：pytest，纯函数模块（SRS scheduler、cleaning、bark）必须有单测

### 2.5 前端：Jinja2 + HTMX + Alpine.js（暂定方案 A）


- **Jinja2**：Flask 服务端渲染，继承 MemoBuddy 模板经验
- **HTMX**：无需写 JS 实现局部刷新、点夯、一起记等交互（`hx-post` / `hx-swap`）
- **Alpine.js**：纯前端状态管理（下拉、展开、开关），替代零散原生 JS
- **无构建工具**：无 webpack / vite，降低维护复杂度
- **P1 无 WebSocket**：Session Pad 推迟至 P2，P1 所有页面均为 Jinja2 + HTMX，无 Socket.IO 引入

React / Vue SPA 暂不采用——Flask 变纯 API 改动太大，solo 开发维护两个项目成本高，HTMX 覆盖 P1 全部交互需求。

**FastAPI 不换，理由已评估（2026-06-22）**：
FastAPI 的优势（原生 async、Pydantic、WebSocket）在以下条件才触发：同时在线数百用户、对外开放 API、Session Pad 成为高频功能。P1 均不满足，迁移成本远大于收益。
LLM service 层设计为可替换接口（见 llm-provider-failover.md），业务逻辑不绑定框架，将来真要迁移只换路由层。

### 2.6 应用层鉴权，无 nginx Basic Auth

- 所有需要登录的路由加 `@login_required`
- **邀请制**：管理员用 `flask create-user` CLI 建账号，不开放公开注册
- 密码 hash 用 **Werkzeug** `generate_password_hash` / `check_password_hash`（无需额外依赖）

## 3. 产品大方向决策

### 3.1 用户模型（两阶段）

| 阶段 | 注册方式 | 说明 |
|---|---|---|
| **P1（邀请制）** | 管理员 CLI 建账号 | 先跑通核心功能，小圈子验证 |
| **P2+** | 开放注册（邀请码或自由）| 同步上社交功能 |

### 3.2 AI API 策略

- 系统内置 DeepSeek key，按**每用户每日 token 额度**限制（防烧）；额度超限后 AI 功能提示"今日额度已用完，可配置自己的 key"
- 用户可在设置页填自己的 DeepSeek key，使用自己 key 时**不计入系统额度**
- 两路 key 对应同一套 AI 逻辑，切来源即可；key 加密存 `user_settings`，使用独立 `DATA_ENCRYPTION_KEY`（不与 session 签名的 `SECRET_KEY` 共用），密文带版本号便于轮换

### 3.3 多语言优先

- 数据模型从一开始支持任意语言，不写死法语
- 每个词表（WordList）记录 `language_code`（如 `fr`、`ja`、`ru`）
- AI 提示词、TTS 语音、清洗逻辑跟随 `language_code`

### 3.4 输入端（P1）

| 方式 | 说明 |
|---|---|
| **CSV 上传** | 用户上传 Aisten CSV，前端调清洗接口，DeepSeek 归一化，入库 |
| **文档抽词 /extract** | 粘贴文章 / 字幕，DeepSeek 抽词 + 结构化，入库 |

邮件自动导入不做（个人飞书邮箱绑定，不通用；用 CSV 上传替代）。

### 3.5 输出端（P1）

| 端 | 说明 |
|---|---|
| 网页复习 + SRS | 首页三按钮；`/stats` 进度看板；`/write` 造句日记 |
| Bark 推送 | 用户配置自己的 device key，存 `user_settings`；dispatch 心跳读每用户配置 |
| 私人播客 | 用户独立 podcast token；edge-tts 共享基础设施，音频按 user_id 隔离 |
| AI 助教 | 对话历史按 user 隔离，会话存 Postgres（不再用独立 chat.db） |

Eudic 同步 P1 不做（每用户 token 管理中等复杂度，优先级低）。

## 4. P1 明确不做（防范围蠕变）

| 功能 | 理由 |
|---|---|
| 公开注册 | P2 再开，P1 小圈子验证 |
| 社交功能（关注 / 动态 / 排行榜） | P2，需 feed 逻辑和额外表 |
| Eudic 同步 | per-user token 管理，P1 不必要 |
| Kindle 每日页 | 设备绑定 + 个人定制，不适合通用用户 |
| 邮件自动导入 | P1 用 CSV 上传替代 |
| 知识图谱 | WordNest 历史包袱，不搬 |
| 移动端 App | Web 优先，P2+ 视需求 |
| **Session Pad** | 技术复杂度高（WebSocket + gevent + guest token），且依赖社交网络前提（需有语言伙伴可用），推迟至用户量达 50-100 后作为 P2 主打功能上线 |

## 5. 高层数据模型（Postgres 表草图）

```
users
  id, email, password_hash, display_name, role(admin|user), created_at, is_active

user_settings
  user_id FK, deepseek_key_enc, daily_token_limit, tokens_used_today,
  bark_url, webhook_url,
  podcast_token, podcast_public_base, eudic_token_enc(预留),
  notify_review_reminder(bool default true),
  notify_daily_summary(bool default true),
  notify_intake_done(bool default true),
  notify_partner_activity(bool default false, P2预留)

word_lists
  id, user_id FK, name, language_code, created_at

words
  id, list_id FK, word, marked,
  due_date, interval, ease, reps, lapses, last_review,  ← SM-2 字段（P1 使用）
  stability FLOAT nullable, difficulty FLOAT nullable    ← FSRS 预留（P2 切换时填入）

definitions
  id, word_id FK, part_of_speech, meaning, example, note

review_logs
  id, word_id FK, user_id FK, ts, grade, source, interval_after,
  stability_after FLOAT nullable, difficulty_after FLOAT nullable  ← FSRS 预留

output_entries                                          ← 造句日记
  id, word_id FK, user_id FK, original, corrected, feedback, has_error, created_at

conversations                                           ← AI 助教
  id, user_id FK, title, created_at

messages
  id, conv_id FK, role, content, ts
```

**P2 预留（P1 不建）**：`follows`（user_id, target_user_id）、`activities`（用户动态 feed）

## 6. 部署拓扑

### 开发阶段（现在）
```
本地开发机
├── Flask dev server 或 gunicorn
├── PostgreSQL（本地安装）
└── 无需云机
```

### 上线阶段（早期：与 MemoBuddy 同机，逻辑强隔离）
```
MemoBuddy 云机（43.156.210.229）
│
├── Linux 用户：rememate（独立，不与 memobuddy 用户共用）
├── 目录：/srv/rememate/
├── venv：/srv/rememate/venv/（独立 Python 环境）
│
├── nginx
│    ├── memo.8853588.xyz:443   → 127.0.0.1:8890  (MemoBuddy，不动)
│    └── rememate.com:443       → 127.0.0.1:8891  (RemeMate，独立 server block)
│
├── gunicorn -w 4 -b 127.0.0.1:8891 wsgi:app
│    P1: sync worker，无 WebSocket
│    P2 Session Pad 上线前切换至 gevent worker (-k gevent -w 2)
│
├── PostgreSQL 15（共用实例，独立 DB + 独立角色）
│    db=rememate，user=rememate（只访问自己的 DB）
│    db=rememate_dispatch，user=rememate_dispatch（BYPASSRLS，仅 dispatch 用）
│    备份：/srv/rememate/backups/（pg_dump + gzip + 14 天轮替，独立于 MemoBuddy 备份）
│
├── 配置：/etc/rememate/rememate.env（独立 env，不与 MemoBuddy 共用）
│    SECRET_KEY、DATA_ENCRYPTION_KEY、DATABASE_URL 均独立
│
├── 日志：/var/log/rememate/
│
└── systemd
     ├── rememate.service              gunicorn 主服务
     ├── rememate-bark.timer           每 15 分钟：复习提醒推送
     ├── rememate-summary.timer        每小时：判断是否到用户本地 08:00，推每日摘要
     ├── rememate-podcast.timer        每小时：TTS 生成播客音频
     └── rememate-backup.timer         每日 03:30 备份

MemoBuddy 所有服务不受影响，继续独立运行。
```

### 对象存储迁移规划

| 内容 | 迁移时机 | 说明 |
|---|---|---|
| podcast 音频文件 | 中期（磁盘压力出现时）| 按 user_id 分目录，迁到 S3/R2 |
| 数据库加密备份 | 中期 | pg_dump + 加密 + 上传，保留本地 3 天副本 |
| 用户上传文件（CSV 不存） | 暂无 | P1 CSV 处理即丢，无需迁移 |
| Bitwarden 主数据库 | **不迁** | 只做加密备份，主数据必须在本机 |

### 迁出独立 VPS 的时机

满足任一条件时评估：
- RemeMate 开放公开注册 → 此时同步评估 Bitwarden 迁机
- 活跃用户 50–100+，dispatch 开始影响主机负载
- Session Pad / WebSocket（P2）上线
- 出现安全顾虑（RemeMate 漏洞风险影响同机 Bitwarden）
