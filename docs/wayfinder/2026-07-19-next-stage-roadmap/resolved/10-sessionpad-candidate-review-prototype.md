# SessionPad 候选审核 UI 原型决议

## Question

候选审核如何同时呈现词语、可编辑短语境、伙伴交换来源和必要词条字段，让用户清楚区分反馈原文、
候选语境和最终例句，又不把移动端变成拥挤表单？

## Prototype method

一次性静态原型比较三种结构：

1. **A：展开卡片流**：每个候选是一张完整表单卡。
2. **B：列表 + 详情**：左侧候选队列，右侧编辑当前候选。
3. **C：单候选聚焦审核**：一次审核一个，接受或忽略后进入下一项。

三种方案覆盖桌面和 390px 移动端，以及长反馈拆词、已有词、缺语境、用户编辑与 AI 不可用。原型
按 Wayfinder 原规则在决策后删除，没有进入 Git；本恢复保留决策契约，不伪造已删除的 HTML。

## Decision

选择 **C 为主，吸收 A 的缺语境空状态和 AI 降级提示**。

- 一次只判断一个词，符合把伙伴反馈整理成可复习词条的任务。
- 语境和最终例句保持视觉分层。
- 桌面和移动端共用同一结构，不依赖双栏。
- 连续“接受/忽略并看下一个”形成明确队列。
- 只约束 `source_type == "sessionpad"` 的待审核候选，不重做 CSV、阅读或文本抽词审核。

## Pending-review layout contract

### 页面与来源

- 保留待审核、已接受、已忽略状态导航。
- 顶部显示轻量来源：伙伴昵称、交换日期、可选会话标题，以及查看复盘或反馈包入口。
- 不在候选卡默认展开整份伙伴反馈。
- 长反馈拆出的多个词逐一出现，来源条保持稳定。

### 主审核区

- 词语或表达是第一层级。
- 直接显示并允许编辑 `context_excerpt`。
- 显示 `原文摘录/source_quote` 或 `用户整理/user_edited`。
- 用户编辑后 provenance 变为 `user_edited`。
- 显示轻量进度，如 `2 / 5`，不制造任务压力。

### 最终例句

- 主区紧凑显示最终例句是否为空。
- “将语境用作例句”只填入可编辑例句草稿，不保存也不自动接受。
- 词性、释义和最终例句放入“释义、词性与例句”高级展开区。
- 用户可以不用候选语境，直接手写最终例句。

### 操作

- 主动作：“接受并看下一个”；最后一项为“接受并完成”。
- 次动作：“忽略并看下一个”。
- SessionPad 待审核队列不提供一键全部接受。
- 已有同语言词条显示“生词本已有”；接受后关联既有词，不创建重复词，也不自动覆盖释义或例句。
- 聚焦队列只约束待审核状态，已接受/已忽略可使用更简单列表。

## State contract

| 状态 | 用户看到什么 | 阻塞接受 |
| --- | --- | --- |
| 原文语境 | 可编辑短语境 + 原文摘录 | 否 |
| 用户编辑语境 | 可编辑短语境 + 用户整理 | 否 |
| 缺少语境 | 安静空状态，可留空或手动添加 | 否 |
| AI 暂不可用 | AI 建议暂不可用，手动审核和入库仍可继续 | 否 |
| 生词本已有 | 已存在提示，接受后关联既有词 | 否 |
| 最后一项 | 接受并完成 | 否 |
| 队列为空 | 本来源已处理完成，返回反馈包或生词本 | 不适用 |

AI 不可用是瞬时交互状态，不进入候选领域字段；缺语境由 `context_excerpt IS NULL` 稳定表达。

## Responsive contract

- 移动端单列；来源、词语、语境、例句状态和动作保持同一阅读顺序。
- 长词、长语境和按钮组不得横向滚动。
- 动作区可换行，但不得遮挡固定底部导航。
- 状态文案不得导致主要动作跳动。

## Rejected alternatives

- A 的所有字段同时展开会让多候选页面过长，移动端尤其难辨当前任务。
- B 的桌面扫描效率高，但移动端失去双栏优势，更像后台数据管理。

## Implementation boundary

- 先完成 WordCandidate 语境字段和服务契约，再接 SessionPad 专用审核。
- 读取和写入显式按 user_id，并让 FORCE RLS 生效。
- 接受、忽略、已有词关联和语境转例句覆盖重复提交与并发。
- AI 提取失败不回滚人工候选，也不阻塞手动审核。
- 不重做通用审核、伙伴关系、反馈包、词库详情或首页复习卡。

原型曾在 Chrome 的 1440x1000 和 390x844 检查，三个方案均无横向溢出。
